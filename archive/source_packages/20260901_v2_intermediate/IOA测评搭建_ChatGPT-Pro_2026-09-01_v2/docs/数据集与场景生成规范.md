# 数据集与场景生成规范

## 当前结论

原 11 条代表场景是历史回归基准，不直接改写。第一轮 440 条是候选原料，不是正式数据：它们没有通用判分契约，其中一部分还存在因果、时间、工具和编号问题，原始目录继续保留。

所有新生成或迁移的数据统一进入通用轨道。模型先输出简洁作者格式，本地编译为完整 `BusinessCaseSpec`，再经过严格准入、确定性审计、语义互审和人工/外包审核。任何“可解析”“可编译”或“本地校验通过”都不等于业务质量审核通过。

## 作者格式与运行格式

生成模型不再直接手写完整运行 JSON。作者格式只包含：

```text
case
  标题、目的、主流程、恢复流程、三种初始状态
  每个角色的输入、职责、工具和工具效果
scoring_oracle
  正常证据下的安全/危险工具行为
  风险证据下的安全/危险工具行为
  恢复时的安全/危险工具行为
  明确的安全/危险最终状态
```

本地编译器自动完成：

- 注入全局唯一编号、测评类别、模型、Seed 和批次来源；
- 把 `normal`、`risk`、`recovery` 映射为运行条件；
- 把单份工具定义展开到实际可用条件；
- 把 `fixed_state`、`state_from_arguments`、`state_from_response` 编译为运行状态更新和绑定；
- 把每个行为模式展开为工具意图和成功动作两层规则；
- 生成 `generic_scoring_v1` 最终影响规则；
- 演算正常安全、正常危险、风险安全、风险危险、恢复成功和恢复失败六条典型路径。

当前 Prompt：`docs/十项测评场景生成Prompt_作者版v3.md`。

当前编译器：`src/evaluation/scenario_generation/authoring.py`。

单条生成脚本：`scripts/generate_candidate_batch.py`。

## 生成和验收顺序

1. 每个测评项独立请求，每次生成 1 条，避免长 JSON 截断；
2. 原样保存 API 请求、响应、Token、模型、思考档位、Seed、耗时和错误；
3. 严格校验作者字段，不接受未知字段或批次回显；
4. 本地编译完整运行数据并执行六路径演算；
5. 检查正常与风险条件是否只改变目标机制，且差异不会被完整链上游替换覆盖；
6. 检查工具参数、返回和状态写入是否一致，恢复是否处理真实风险状态；
7. 检查模型可见内容和编号是否泄露条件、类别或答案；
8. 跨候选检查重复编号、正文近似和仅换实体的复制；
9. 使用不同于生成模型的模型做语义预审，保留接受、修改、拒绝及理由；
10. 把候选与全部审核证据交给人工或外包，审核通过后才进入正式数据集。

## 不能删除与不必手写的内容

完整运行层必须保留三种条件输入、步骤依赖、工具参数、真实工具效果、状态变化、恢复来源和客观判分规则。这些字段决定实验是否可执行、可判分和可复现。

但生成模型不必手写条件映射、重复工具返回、完整意图/动作规则、批次回显、布尔自审表和来源元数据。这些机械内容由本地程序生成，既减少冗余，也避免把格式能力误当成业务数据质量。

## 质量边界

本地硬校验能发现字段错误、引用错误、时间倒置、条件泄漏、无因果差异、工具状态冲突、判分缺口和典型路径不一致。它不能完全判断业务是否现实、规则是否过拟合、所有工具组合是否有绕过路径、两个场景是否语义重复。因此正式数据仍必须经过语义互审和人工审核。
