## 2. 用户要求的测评原则

这是对 Agent 模型在 IOA 场景下表现的测评，不是让测评程序教模型给出安全答案。

必须遵守：

1. 模型做出危险决定不等于程序出错。危险决定本身可能就是测评结果。
2. 不得在模型输入中加入“应拒绝、应谨慎、应先核验、正确做法”等答案提示。
3. 可以严格规定输出字段和工具调用格式，但不能规定模型必须作出哪种业务决定。
4. 必须分别记录模型的工具请求、系统是否真正执行、工具返回值和最终影响。
5. 不得把模型文字中声称执行过的动作，当成系统真的执行了动作。
6. 不得为了让结果看起来安全而修改模型原始回答。
7. 后一个 Agent 只能收到流程规定允许传递给它的信息。

### 3.2 被测 Agent 只采用第一次回答

此前八项测评中，如果 Agent 第一次回答格式不符合要求，Gateway 会自动再次调用同一个 Agent，让它重新整理格式，并使用第二次回答继续测评。

现在已经改为：

1. 结构化输出要求在第一次调用前提供给模型。
2. 第一次回答是该步骤唯一的被测回答。
3. 第一次回答格式错误或结构化字段互相矛盾时，直接将该步骤记为无效。
4. 不再自动第二次调用被测 Agent 整理格式。
5. 完整保留第一次接口请求和第一次原始回答。
6. 失败记录写入：
   - `tested_response_policy=first_response_only`
   - `format_correction_attempted=false`
7. 该类失败归为 `INVALID_PARSE_FAILURE`，不再笼统归为普通执行失败。

## 7. 处理测试失败的规则

每个失败项都要先分到下面三类之一：

### A. 正式代码问题

例如：

- 工具参数限制没有实际生效。
- 最终回答和工具调用可以同时出现。
- 后一个 Agent 没收到本应收到的上游输出。
- 模型第一次格式错误后仍然发生第二次被测 Agent 调用。
- 第一次原始回答没有进入完整记录。
- 危险但格式正确的回答被程序改写或替换。

这种情况应修复正式代码，并增加能够复现问题的测试。

### B. 测试仍按旧设计编写

例如测试要求重新显示已经有意删除的重复字段、内部身份或空区块。

这种情况应更新测试，但必须先说明旧断言为什么与当前需求冲突。不能仅为了让测试变绿而删除合理断言。

### C. 本机环境问题

例如解释器不一致、依赖未安装或路径错误。

本机应优先使用仓库解释器：

```text
.\.venv\Scripts\python.exe
```

不要直接假定 `python`、`pip` 和 `py` 指向同一个环境。

## 8. 离线假模型测试的作用和限制

结论：不是必须，但建议在真实模型运行前执行一次。

它能快速检查：

- 八项案例能否加载。
- 普通、风险、恢复三个阶段能否进入。
- 多轮流程是否能继续执行。
- 数据库和结果目录能否创建。
- 完整记录和易读记录能否生成。
- 某些工具、状态传递和结果汇总代码是否会直接报错。

它不能检查：

- 真实模型是否理解输入。
- 真实模型是否按要求输出。
- 真实模型是否调用工具。
- 真实模型是否作出危险决定。
- API 的真实返回格式、停止原因和长度问题。
- Judge 对真实回答的判断是否合理。

当前离线固定回答程序不一定能生成每一项都符合严格结构的业务回答，因此出现大量 `INVALID` 不等于八项正式代码一定有问题。离线结果不能用于评价模型安全性，也不能代替真实模型运行。

如果已经成功完成真实模型八项运行，并且逐项检查了流程和记录，离线测试不是必须补跑。但建议先跑离线测试，因为它不调用付费接口，可以提前发现文件、流程和记录生成方面的明显错误，避免浪费真实模型请求。

本次交接已经要求 DeepSeek 将它作为第一项检查。命令与第 5.2 节相同：

```powershell
.\.venv\Scripts\python.exe scripts\run_agent_model_suite.py `
  --run-purpose smoke `
  --execution-mode offline_deterministic `
  --repeat-count 1 `
  --output results/deepseek_offline_eight_20260802_round1
```

运行后必须确认 `execution_mode=offline_deterministic`、`offline_fake_model=true`、`provider_request_count=0`，不能把它误写成真实模型结果。

真实运行后逐项检查：

1. 每个 Agent 的实际接口输入是否完整、整洁、没有答案提示。
2. 原始回答和解析后回答是否一致。
3. 是否只有格式合法的第一次回答进入后续流程。
4. 工具请求、实际执行、返回结果是否分别记录。
5. 工具参数是否在当前案例允许范围内。
6. 后一个 Agent 是否收到流程规定的上游信息。
7. 最终状态是否与工具和消息记录一致。
8. Judge 标签是否有真实证据支持。
9. 是否生成完整追溯记录。
10. 是否生成八项各一份的易读流程记录。

## 10. 必须保留的两种记录

完整追溯记录至少应包含：

- 实际接口消息。
- 实际请求参数。
- 每次接口返回。
- 停止原因。
- token 使用量。
- 工具请求和工具结果。
- 失败、重试和状态变化。
- Agent 对后续流程的真实影响。

八项易读记录应分别展示：

- 当前测评目标。
- 每个阶段和每个 Agent 的顺序。
- Agent 实际收到的输入。
- Agent 原始输出和易读整理。
- 工具请求、参数、结果。
- 系统执行或拦截情况。
- 后续 Agent 收到的信息。
- 最终结果和必要注释。

易读记录可以把超长 JSON 字段结构转成中文字段表，但必须注明“已转为易读形式”，不能删掉影响判断的业务信息。
