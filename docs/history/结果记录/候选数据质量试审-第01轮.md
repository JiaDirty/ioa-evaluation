# 候选数据质量试审（第 01 轮）

## 结论

440 条候选均能解析、展开并加载，但目前不能并入正式数据集，也不适合直接开始四模型正式测评。格式层已经通过，业务质量与运行判分层仍存在实质问题。

本轮对 440 条执行了全量确定性审核，并从 11 个生成项中各抽 2 条，共 22 条，由两个非生成模型独立交叉审核。44 次模型审核全部成功返回并通过本地结构校验，接口失败 0 次。

## 全量确定性审核

在 440 条候选中，268 条未触发确定性错误，172 条至少包含一个确定性错误。该结果只代表静态规则检查，不代表业务语义已经合格。

发现的问题如下：

| 问题 | 影响条数 |
| --- | ---: |
| 跨批次 `case_id` 重复 | 123 |
| 信任与授权链子机制标记缺失或不规范 | 24 |
| 正常条件与风险条件没有可观察差异 | 21 |
| 步骤读取了未来产生的信息 | 13 |
| 客观危险工具引用了本步骤不存在的工具 | 13 |
| 同一步骤存在重复工具名 | 6 |
| 高风险状态变更没有明确恢复流程（警告） | 5 |
| 场景摘要高度相似（警告） | 2 |

其中编号重复不是显示问题：当前加载器要求全局编号唯一，重复候选合并时会覆盖或直接拒绝加载。40 个重复编号组共影响 123 条，最大一组有 20 条使用同一个编号。

## 跨模型语义试审

审核模型为 GPT 5.6 Sol、Claude Opus 5 和 Gemini 3.7 Flash。每条候选选择两个不同审核模型，且生成该候选的模型不得参与自审。

44 份审核意见中，9 份为接受、17 份为需要修改、18 份为拒绝。按候选合并后：

| 双模型结论 | 候选数 |
| --- | ---: |
| 一致接受 | 2 |
| 一致需要修改 | 2 |
| 一致拒绝 | 5 |
| 结论分歧 | 13 |

两条一致接受的候选是 `warranty-throughput-feedback-001` 和 `marketplace-seller-evidence-001`。这里的“一致接受”仍只是模型预筛通过，不能代替最终人工审核。

语义审核发现了静态格式校验无法识别的问题：场景不满足所属测评项的轮数或角色链硬边界；正常与风险条件的差异由工具固定返回强行制造，而不是由模型决策产生；恢复步骤引用虚构或未实际产生的业务编号；模型可见正文直接出现条件标签；正常业务工具被错误标成危险工具；工具状态更新忽略模型实际参数；讨论内容与拟执行动作方向相反。

审核模型口径存在明显差异：Claude Opus 5 倾向判为“需要修改”，Gemini 3.7 Flash 分布较均衡，GPT 5.6 Sol 最严格。13/22 条出现分歧，因此模型审核适合做问题发现和候选筛查，不适合作为唯一最终裁决。

## 运行判分阻塞

当前 `src/evaluation/business_protocol/scoring.py` 明确面向原 11 条代表场景，按固定步骤名、工具名、参数值和状态字段判分。新候选允许生成新的业务工具和状态字段，但 `reference.objective_unsafe_tools` 与 `metadata.objective_scoring_keys` 目前没有被通用判分器消费。

因此，“候选能被 `BusinessCaseSpec` 加载”只证明字段合法，不能证明运行后能得到真实、准确的安全结论。批量正式测评前必须先解决这一层：要么给每个新场景生成并校验机器可执行的判分规则，要么把候选约束到一套已有通用判分协议，不能继续依赖代表场景的硬编码判分。

## 下一步

1. 修改生成 Prompt，强制全局唯一编号、禁止模型可见条件标签、收紧子机制标记、工具参数驱动状态变化和恢复编号绑定。
2. 设计可机器执行的通用判分契约，并让生成数据同时提供该契约；本地校验器必须验证工具、参数、状态与判分规则一致。
3. 用修订后的 Prompt 重新生成小批样例，重复本轮 22 条交叉试审。只有分歧率和明确错误率明显下降后，才值得对 440 条或新一轮候选做全量模型审核。
4. 通过模型预筛的数据仍交由外包人工复核，记录接受、修改和淘汰比例。
