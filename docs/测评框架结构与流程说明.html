IoA Layer Evaluation Framework v0.1

IoA 层智能体安全测评框架结构、内部实现与整体流程

本页面用于说明当前 IOA 测评搭建项目的可交付内容：它不是单一 Agent 的能力测试，而是面向开放智能体生态的安全测评环境。框架通过 Sub-IoA 子生态、注册发现、网关协同、协议适配、共享知识、审计链路、攻击注入和 LLM Judge，把“开放生态中的安全风险”转化为可运行、可记录、可复现实验。

一、框架定位：为什么要单独做 IoA 层测评

IoA 层关注的是多个异构智能体系统连接之后产生的生态级风险。传统单 Agent 安全测评通常检查模型输出是否有害、工具调用是否越权、单次任务是否成功；而 IoA 场景中，风险往往来自跨域发现、身份信任、协议转换、委托链路、共享知识污染、声誉机制操纵、群体讨论偏移等“系统交互效应”。

不是普通 MAS Demo 当前框架强调开放生态中的动态注册、跨域发现和异构协议，而不是预先写死的多智能体协作脚本。
不是只测模型回答 风险判断同时看任务结果、审计链、授权范围、注册信息、知识库冲突、协议协商和攻击后状态变化。
面向论文实验 每条 seed 场景都对应风险维度、攻击方法、防御要求、预期指标，便于后续扩展为 benchmark 和消融实验。
对学长可以这样概括：本项目已经把“IoA 层风险分类”落成了一个可运行测评框架，能把风险 taxonomy 里的 18 个子风险映射为场景、攻击、执行链路和实验报告。

二、总体三层架构

1. 实验控制层 Experiment Control Layer

负责实验编排、拓扑控制、场景加载、攻击注入、指标计算、LLM Judge 判定和报告生成。核心入口集中在 src/experiment/runner.py 与 run_experiment.py。

IoAEnvironment ExperimentRunner TopologyController MetricsEngine AttackInjector LLMJudge
2. IoA 基础设施层 IoA Infrastructure Layer

提供开放智能体生态的公共基础设施，包括全局注册表、任务市场、协议协商与适配、共享知识库、全局审计日志。它构成可控 IoA testbed，用于复现不同 Sub-IoA 之间通过基础设施互联后的安全行为。

Global Registry Task Marketplace Protocol Adapter Shared Knowledge Base Global Audit Logger
3. 子生态层 Sub-IoA Layer

每个 Sub-IoA 表示一个局部智能体生态，例如金融、医疗、旅行、新闻。每个子生态拥有本地注册表、本地审计、唯一网关和若干 Agent，外部请求必须经由 Gateway 进入。

四、整体测评流程

当前框架有两条互补路径：第一条是代码级风险测试路径，直接运行 risk_tests 中的 18 个测试；第二条是数据驱动 benchmark 路径，从 data/seeds/*.json 加载场景，构建环境并执行对应任务。两条路径最终都汇入统一报告。

4.1 数据驱动 benchmark 流程

1. Seed JSON每条 seed 描述风险维度、子风险、Sub-IoA、Agent、任务、攻击、防御和预期指标。
2. ScenarioLoader解析为 Scenario 数据类，避免临时字符串拼接，保证字段结构稳定。
3. setup_from_scenario创建子生态、注册 AgentCard、注册 Gateway、加载共享知识和拓扑。
4. TaskMarketplace根据任务类型选择单域、跨域、多跳或 artifact 复用执行方式。
5. Gateway执行鉴权、发现、验证、协议协商、任务中继和安全检查。
6. Agent 执行Gateway 通过协议适配器 POST 到 Agent endpoint；本地 endpoint 再调用对应 AgentCard 的真实 LLM runtime。
7. Audit & Artifact记录任务链路、参与 Agent、协议、授权、输入输出产物和安全状态。
8. Attack Injector在指定组件上注入身份、注册、协议、知识、声誉或人机能动性相关攻击。
9. Judge & Metrics结合规则指标与 LLM Judge，判断攻击是否成功、防御是否生效。
10. Report输出 summary、category_breakdown、test_results、task_results 和反馈建议。

4.2 代码级风险测试流程

测试入口

risk_tests/registry.py 中的 ALL_TESTS 注册 18 个风险测试。运行实验时，Runner 逐个调用测试对象，测试对象操作环境状态并返回 TestResult。

测试输出

每个测试输出是否通过、风险等级、观测指标、证据和说明。最后由 MetricsEngine.generate_report() 汇总到 JSON 报告。

五、Gateway 内部 8 步执行逻辑

Gateway 是当前框架中最能体现 IoA 特征的模块。每个 Sub-IoA 对外只暴露 Gateway，所有跨域调用都必须经过它，因此它天然成为授权、协议、审计和责任归因的控制点。

Step 1 Task Intake接收任务，写入调用审计，生成 trace。
Step 2 Auth Check检查 requester 是否存在、是否 active、权限范围是否覆盖任务。
Step 3 Local Discovery在本地 Registry 中按能力搜索候选 Agent。
Step 4 Cross-Domain本地无匹配时转向 Global Registry 跨域发现。
Step 5 Verify & Rank过滤未验证、异常或声誉不足候选，并按优先因子排序。
Step 6 Negotiation在 A2A、MCP、PRIVATE_API 中协商可用协议。
Step 7 Relay将任务转换为目标协议消息，调用目标 Agent 或目标 Gateway。
Step 8 Security & Audit检查输出 artifact 安全性，写入本地和全局审计日志。
最近已补齐 Gateway 自身的基础设施身份注册：跨域转发时，源 Gateway 会作为 requester 进入对方 Registry 的鉴权逻辑，因此 Gateway 也需要被注册为拥有 relay/delegate 权限的基础设施 AgentCard。这个修复解决了跨域场景中的授权失败问题。

七、报告与指标体系

实验报告由 MetricsEngine 生成，主要包括摘要、分类统计、单项测试结果、任务执行结果和审计指标。当前指标核心是把任务可用性、安全性、可追踪性、风险遏制能力放入统一评估框架。

Utility

任务完成率。衡量系统在安全约束下是否仍能完成协作。

Safety

攻击是否被阻断，输出 artifact 是否安全，风险是否被判定。

Traceability

审计链完整性、归因准确性、来源覆盖率。

Containment

风险是否被限制在局部，是否出现跨域或多跳扩散。

报告结构

字段含义
summary总测试数、通过数、失败数、任务完成率、审计指标。
category_breakdown按 6 个风险维度统计每类风险的测试通过情况。
test_results每个风险测试的判定结果、风险等级、指标和证据。
task_results任务执行输出、参与 Agent、产物 artifact 和状态。
feedback_loop/actions后续可加入自动反馈、修复建议或防御策略迭代。

九、后续补充与论文化方向

1. 增加实验重复与统计检验

正式实验保持 live LLM 与真实 endpoint，增加重复运行、均值、方差、置信区间和无效样本统计。

2. 扩充 benchmark 规模

当前每个子风险有 1 条 seed，后续可扩为每个子风险 3 到 5 条，形成更稳定的统计结果。

3. 指标体系论文化

把 Utility、Safety、Traceability、Containment 和 IoA-ERS 明确定义为公式、测量方法和实验表格。

4. 做消融实验

比较关闭 Gateway 鉴权、关闭审计、关闭共享知识冲突检测、不同拓扑结构下的风险变化。

5. 与 TrinityGuard 方法对齐

把“攻击构造、目标系统执行、判据裁判、证据记录、风险分级”整理成统一实验协议。

6. 前端可视化增强

增加拓扑图、审计链路图、风险热力图、单个 seed 的执行轨迹回放，提升答辩展示效果。
