# 统一数据格式与端到端生成流程

## 当前实现

项目现在以一套可执行数据格式、一套 Registry 和一个 `PipelineOrchestrator` 作为生产主线。旧的 11 条回归基准与后续 440 条候选进入系统后不再按来源选择流程；来源、模型、Prompt、Seed 和版本只作为可追溯元数据保存。

这里的“统一”指统一数据契约和执行语义，不是把所有场景写成相同的业务内容。每条数据仍然可以有不同的测评类别、角色、工具和业务状态，但都必须能表达为同一个规范化案例。

## 四层规范化案例

每条数据都必须按下面四层顺序保存和推进：

```text
ScenarioTask
  → ScenarioKernel
  → EffectSpec
  → CompiledCase
```

`ScenarioTask` 是唯一输入外壳，携带规范化业务案例和可追溯元数据；
`ScenarioKernel` 描述因果和角色；`EffectSpec` 描述工具效果与判分契约；
`CompiledCase` 是可交给运行器的最终案例。

类别差异和机制差异放在字段中，不再新增按类别写死的 Python 判分函数。判分只检查模型消息、工具调用、工具返回和业务状态变化等可观察证据。

## 从生成到冻结

```text
任务需求
→ ScenarioTask
→ ScenarioKernel
→ EffectSpec
→ CompiledCase
→ 六路径确定性验证
→ 运行层冒烟
→ 两个独立模型语义审核
→ 人工终审
→ Registry 登记、哈希封存、冻结入库
```

上述前三个阶段由 `PipelineOrchestrator.submit/process/resume` 统一控制，状态中心只有
`registry.json`；每条数据只使用一个目录，并保存 `scenario_task.json`、
`scenario_kernel.json`、`effect_spec.json`、`compiled_case.json` 和 `lineage.json`。

六路径是统一的质量验证矩阵，不是两套数据运行路径：正常安全、正常危险、风险安全、风险危险、恢复成功、恢复失败。只有编译通过、六路径全部通过、运行证据完整且审核接受的案例，才能进入正式数据集。

每个阶段都保存版本、输入哈希、输出哈希、失败原因和可复现参数。真实 API 阶段必须显式启用，并把原始请求和响应写入独立证据目录；默认离线命令不产生网络请求。

## 旧数据迁移规则

### 11 条历史基准

11 条旧场景已经转换为 `ScenarioTask → ScenarioKernel → EffectSpec → CompiledCase`，并写入同一个 Registry。等价回归脚本 `scripts/run_legacy_equivalence.py` 对 11/11 条结构和危险向量均通过；旧实现只作为回归基准隔离保存，不再被正式入口调用。

### 440 条候选

440 条候选必须经过同一套规范化、编译、六路径验证和审核。当前第一轮只完成离线登记：440 条源哈希匹配、440 个任务卡、440 个 `ScenarioKernel` 和 `EffectSpec` 草案；`EffectSpec` 仍为 `DRAFT`，其中 369 条需要修复、71 条需要重写，不能直接进入正式实验。

## 当前实现边界

当前仓库已经具备四层模型、统一 Registry、单一 `PipelineOrchestrator`、一次性迁移脚本、依赖哈希失效和可复现文件保存。`pipeline_runner.py`、`unified_pipeline.py` 与固定判分入口已从包级导出和正式命令中隔离，仅供等价回归测试读取；正式代码、测试命令和数据迁移均走 `unified_architecture.py`。

正式推进前先抽取每个类别/机制的代表性样本做 22 条试点。试点需要在同一规范下完成迁移、编译、六路径验证、独立语义审核和人工终审；试点暴露的问题先回写到 Schema、Prompt 和校验器，再批量迁移剩余候选。
