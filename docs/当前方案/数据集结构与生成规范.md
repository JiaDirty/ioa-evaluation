# 数据集结构与生成规范

## 结论

现有单条数据确实存在冗余，但不能通过直接删字段解决。正确做法是区分：

1. **作者格式**：共享常量只写一次，每条数据只保留差异；
2. **运行格式**：执行前展开成完整对象，保证单次运行自包含；
3. **交换格式**：完整 JSONL，便于审计、校验和跨环境使用；
4. **生成批次记录**：模型、Seed、Prompt 版本和排除清单放在批次层，不在每个场景重复。

## 已完成的去冗余

八项160条作者数据现在使用：

```text
data/agent_model_cases/_shared_defaults.json
  + data/agent_model_cases/<CATEGORY>.jsonl
  -> CaseLoader 展开并严格校验
  -> data/generated/...160条.jsonl
```

共享默认值包括：

- `schema_version`；
- `model_config`；
- `data_policy`；
- `visibility_policy`；
- `context_policy`；
- `result_layers`；
- 每个类别内固定的名称、风险类型、角色和执行配置；
- 类别内完全相同的行为定义与指标。

每条作者数据仍保留：

- `case_id`、`category_code` 和业务标题；
- 本场景的业务领域、任务和角色差异；
- baseline、mechanism、recovery 的真实差异；
- 权威工具夹具和状态变化；
- 本场景特有的判分边界；
- 无法安全抽取的历史兼容字段。

## 不能盲目删除的内容

以下内容看起来长，但直接影响能否运行或客观判分：

- 三条件输入和初始状态；
- 每个步骤的角色职责、依赖关系和业务时间；
- 工具参数、响应和状态更新；
- runtime binding，用于 recovery 继承机制阶段真实编号；
- 客观评分规则；
- INC 的多轮独立材料和 DIS 的多参与者状态。

INC 单条数据明显更大，主要因为每个用例包含多轮且互不重复的受控材料。这部分不是简单重复，压缩时不能把不同轮材料合并成一个模板，否则会改变被测输入和实验难度。

## 十项新场景格式

十项扩增统一生成 `BusinessCaseSpec` 候选。批次外层保存：

```text
prompt_version
generation_status
generation_config
cases
batch_audit
```

模型、批次、Seed 和排除数量只保存在 `generation_config`。每个 case 不再重复 provenance，也不要求模型自报不可核验的内部淘汰数和通过率。质量通过情况由结构校验、因果差异检查和人工审核计算。

生成批次的真实 Pydantic 模型位于 `src/evaluation/scenario_generation/models.py`。保存 AIHubMix 原始 JSON 后先运行：

```powershell
.\.venv\Scripts\python.exe scripts\validate_scenario_generation.py <批次文件.json>
```

## 数据进入正式集合前的门槛

1. JSON Schema 与 Pydantic 校验通过；
2. baseline 和 mechanism 只改变目标机制变量；
3. 动作工具按参数和状态执行，不按条件名切换结果；
4. recovery 使用机制阶段真实运行产物；
5. 模型可见输入不包含类别、风险标签或答案提示；
6. 与已有场景不存在浅层换名重复；
7. 离线协议运行全部 `VALID`；
8. 人工复核接受后才能冻结进入 holdout。

AI 生成的内容始终是候选池，不能直接作为正式数据集或论文结果。
