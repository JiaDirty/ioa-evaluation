# 可扩充评测数据架构

当前评测体系分为两条互不混用的兼容轨道。

`legacy_reference` 只服务于原 11 条代表性场景。它们的编号、类别和规范化内容哈希登记在
`data/legacy_reference_manifest.json`，继续使用原来的专用运行和判分逻辑。任何内容变化
都会使哈希失配并被拒绝，因此历史实验语义可以稳定复现。

`generic_expandable` 是以后新增数据的唯一正式扩充接口。它不限制数据条数，不要求一个
目录同时包含全部测评类别，也不依赖固定工具名、步骤名或状态字段。每条数据必须携带
`generic_scoring_v1` 通用判分契约，并用 `state_bindings` 声明工具参数或返回如何改变业务
状态。新增数据只改 JSON 或 JSONL，不需要增加 Python 判分分支。

## 通用数据流

```text
JSON / JSONL 文件或目录
  -> BusinessCaseSpec 严格字段校验
  -> 通用数据集准入校验
  -> 正常与风险条件的因果对照校验
  -> 工具、状态绑定和判分契约交叉校验
  -> BusinessProtocolRunner 通用运行分支
  -> 意图、动作、最终影响三层判分
```

统一入口为 `scripts/run_evaluation_dataset.py`。它默认只接受通用可扩充数据；缺少判分
契约、复用旧基准编号、契约引用不存在的工具或状态字段、存在未来信息或因果对照失效时，
都会在模型调用前停止。

```powershell
.\.venv\Scripts\python.exe scripts\run_evaluation_dataset.py `
  --validate-only `
  --data <场景文件或目录>
```

可以重复使用 `--data` 组合多个文件和目录。目录默认只读取直接子文件；确需读取多层目录
时显式添加 `--recursive`。校验结果会报告数据条数、中文测评类别分布、判分契约版本、
来源文件数和计划结果数，且 `--validate-only` 不会调用模型。

真实模型运行沿用双开关保护：

```powershell
.\.venv\Scripts\python.exe scripts\run_evaluation_dataset.py `
  --data <已审核数据目录> `
  --execution-mode agentic-live `
  --allow-live-api
```

## 新增一条数据需要提供什么

每条数据仍使用完整 `BusinessCaseSpec`：场景身份、主流程步骤、恢复步骤、初始状态、工具
定义、状态绑定、参考摘要、元数据和通用判分契约。判分契约必须对主要步骤和恢复步骤分别
覆盖安全与危险的意图、动作，并对三种条件覆盖安全与危险的最终影响。

这套结构解决的是“新增数据不用修改代码”。它不等于“模型生成的数据自动具备科研质量”。
结构和契约校验通过只表示数据能被一致地加载、运行和判分；业务逻辑、因果设计、重复度
和科学性仍要经过模型预审及最终人工审核。

## 旧数据如何处理

原 11 条继续由 `scripts/run_ten_item_evaluation.py` 运行，不改数据、不改旧判分口径。
第一轮 440 条候选虽然外层格式相似，但没有通用判分契约，不能进入可扩充入口，也不会
再因为缺少契约而自动落入旧专用规则。它们可以保留为历史生成证据；要重新利用，必须为
每条补齐并审核通用判分契约，或者按新版 Prompt 重新生成。
