# 可扩充评测数据架构

当前对外只有一个评测入口：`scripts/run_unified_evaluation.py`。它接收一个文件、多个文件或一个目录，逐条加载场景并按数据中声明的规则运行。入口不限制数据条数，也不要求目录必须同时包含全部测评项。

生产侧现在只有一个不调用模型的规范控制器：`scripts/run_canonical_pipeline.py`。它只接受
`ScenarioTask`，并统一写入 ScenarioKernel、EffectSpec、CompiledCase、lineage 和
`registry.json`；来源只作为追溯元数据，不选择流程。

历史评测入口仍保留兼容适配器以复现已完成结果，但它不参与规范化生产，也不再由生产代码按来源选择流程。所有新增或迁移的数据都必须先完成 `ScenarioTask` 规范化，再由唯一控制器推进；只有编译后的案例才进入统一运行器。

## 两层数据，而不是让作者手写全部运行细节

完整运行数据确实较长，因为它同时承担三项职责：给智能体提供业务事实和工具、让本地工具环境产生可复现状态、让判分器读取客观证据。删掉其中任一层，流程仍可能“跑起来”，但无法证明结果真实或可复现。

复杂度不应全部交给数据作者或生成模型。当前新增数据采用两层结构：

```text
简洁作者格式 v3
  业务流程 + 条件输入 + 工具效果 + 简洁判分依据
        ↓ 本地编译器
完整 BusinessCaseSpec
  条件映射 + 状态绑定 + 意图/动作规则 + 最终影响规则 + 来源信息
        ↓ 严格准入
统一运行器
```

作者格式不要求模型回填批次参数、编号、类别代码、自审布尔表或完整 `scoring_contract`。工具只定义一次；本地自动展开正常、风险和恢复可用条件。每个关键步骤只需按正常、风险或恢复语境列出安全/危险工具行为，本地自动生成意图和实际动作两层规则。Prompt 位于 `docs/十项测评场景生成Prompt_作者版v3.md`，编译器位于 `src/evaluation/scenario_generation/authoring.py`。

编译器还会演算正常安全、正常危险、风险安全、风险危险、恢复成功和恢复失败六条典型路径。六条路径的工具效果与最终判分不一致时，候选不会写入可运行数据。该演算仍不能替代业务语义和对抗性组合审核，候选随后还要经过确定性审计、模型互审及人工审核。

## 统一数据流

```text
JSON / JSONL 文件或目录
  -> BusinessCaseSpec 严格字段校验
  -> 统一数据集准入校验
  -> 正常与风险条件的因果对照校验
  -> 工具、状态绑定和判分契约交叉校验
  -> ScenarioTask → ScenarioKernel → EffectSpec → CompiledCase
  -> 统一运行入口（仅接收编译后的案例）
  -> 输出轨迹、状态变化和判分证据
```

验证而不调用模型：

```powershell
.\.venv\Scripts\python.exe scripts\run_unified_evaluation.py `
  --validate-only `
  --data <场景文件或目录>
```

实际运行沿用双开关保护：

```powershell
.\.venv\Scripts\python.exe scripts\run_unified_evaluation.py `
  --data <已审核数据目录> `
  --execution-mode agentic-live `
  --allow-live-api
```

## 新增数据只需要描述什么

一条通用数据包含场景身份、主流程步骤、恢复步骤、初始业务状态、工具定义、工具参数或返回如何改变状态的 `state_bindings`，以及 `generic_scoring_v1` 判分契约。契约用数据规则说明：

- 哪些工具调用或结构化决定表示安全/危险意图；
- 哪些成功工具调用和动作后状态表示安全/危险动作；
- 最终业务状态在三种条件下怎样算安全或危险。

规则只能读取运行轨迹中已经记录的工具意图、成功返回、动作前后状态和最终状态，不能包含 Python、正则或其他可执行代码。因此新增工具名、步骤名、状态字段和行业场景都不需要修改 Python 判分代码。

这些是编译后的运行字段，不是要求生成模型逐项手写的作者字段。作者层把参数驱动状态写成 `state_from_arguments`，把固定效果写成扁平点路径 `fixed_state`，把最终安全/危险状态写成简洁判据；编译器负责生成运行层字段并交叉检查引用。

## 共享流程和恢复策略

数据可以通过 `execution_plan` 声明：

- `pairing=independent`：正常条件和风险条件分别从各自初始状态运行；
- `pairing=shared_prefix`：公共前缀只执行一次，然后从声明的状态分叉；公共前缀轨迹保留在审计中，但不重复计入条件差异判分；
- `recovery_policy`：风险影响出现时恢复、始终恢复或不运行恢复；
- `recovery_step_ids`：只选择指定的恢复步骤。

这些选项是数据字段，不是类别专用代码。省略时使用与旧数据兼容的默认值。

## 原 11 条和候选数据的统一边界

原 11 条位于 `data/scenarios/`，编号和规范化内容受 `data/legacy_reference_manifest.json` 锁定。迁移脚本会把它们包装为 `ScenarioTask`；旧固定运行和判分只作为结果回归适配器保留，不作为生产流程分支。

第一轮候选的原始请求、响应和展开结果位于 `data/candidate_batches/`，原始目录保持不动。候选只有在能从自身声明的工具、状态变化和恢复动作中明确推导判分契约后，才会进入通用数据集；“能读进来”不等于“可以正式判分”。

已提供迁移命令：

```powershell
.\.venv\Scripts\python.exe scripts\migrate_candidate_contracts.py
```

命令会在指定的 `data/candidate_migrations/<批次>/` 生成三个结果：

- `migrated_cases.jsonl`：从候选中明确推导出工具/状态判分规则、并通过严格准入的数据；编号已重新生成，原编号和生成来源写入元数据；
- `quarantine.jsonl`：无法不带猜测地补齐规则，或存在因果、依赖、时间、工具引用等确定问题的数据及原因；
- `migration_summary.json`：数量、原因统计和产物路径。

迁移脚本只做可证明的修复，例如从批次目录恢复信任链子机制标记；不会擅自改写业务内容、删除工具或把模型没有执行的动作判成安全。迁移后的契约是草案，仍需语义互审和人工/外包审核，不能直接作为最终数据集。

多个迁移批次合并时使用：

```powershell
.\.venv\Scripts\python.exe scripts\merge_migrated_datasets.py `
  --source data\candidate_migrations\第10轮-蓝图v9.2全量迁移 `
  --source data\candidate_migrations\第12轮-授权链迁移 `
  --output data\candidate_datasets\统一通用候选-第01轮
```

合并器会再次按 `generic_expandable` 校验全部编号、契约版本和规则引用，并写出一个可直接交给统一入口的 `accepted_cases.jsonl`。无法可靠推导契约的候选留在各批次的 `quarantine.jsonl`，不会被删除，也不会被伪造规则放行。

## 质量边界

结构和契约校验通过，只说明数据可以被统一加载、运行并给出可复核的规则结果，不等于业务设计已经科学或没有重复。正式纳入前仍要检查业务合理性、正常/风险的因果对照、工具参数与状态变化、恢复是否真实绑定风险产物、信息是否泄露判分答案，以及跨候选的重复度。

当前统一数据模型、状态中心、流程控制器和迁移入口已经完成。原 11 条的旧运行/判分实现只承担历史结果回归；完成等价性回归后即可删除这些兼容代码，不会影响新的统一数据主线。
